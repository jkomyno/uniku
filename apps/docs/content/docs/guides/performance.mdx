Generation speed is a primary design constraint in uniku. Results depend on the format: in this snapshot, Nanoid 6 and BSON ObjectID generate faster than uniku, while the other measured formats favor uniku. Application performance still depends on where and how IDs are created.

## Generation speed

This snapshot comes from a [four-repetition CI run](https://github.com/jkomyno/uniku/actions/runs/43760726485) on November 15, 2026 (UTC), using Node.js 25.9.0 on a GitHub-hosted `ubuntu-latest` runner. The measured library revision is [`6d0725e`](https://github.com/jkomyno/uniku/commit/6d0725eb2aa36c46cbaf911d7cd545f24892781a). Its library source, reference dependencies, runtime pins, and benchmark inputs are unchanged in [`ca8b953`](https://github.com/jkomyno/uniku/commit/ca8b953fa008df06a301ee4c6e3809aef78de6b9).

Each ratio divides uniku's median throughput by the reference package's median throughput. Values above 1 favor uniku; values below 1 favor the reference. These are approximate shared-runner measurements, with noticeable variation in some reference rows, rather than guarantees for every runtime or workload. [Recorded results](https://github.com/jkomyno/uniku/blob/bc4d71d7de105c465b4e6d17da34848081000ca2/baseline.json) preserve the action-level measurements; the [rolling baseline](https://raw.githubusercontent.com/jkomyno/uniku/gh-benchmarks/baseline.json) tracks later CI runs.

The [compatibility benchmark](https://github.com/jkomyno/uniku/blob/main/packages/uniku/__tests__/bench/compat.bench.ts) runs each implementation in a fresh process. CI balances both launch orders across four repetitions and reports the per-row median, so warmed runtime state and one noisy run do not decide the comparison.

## Bundle size

Every entry point is independently importable and tree-shakeable: importing `uniku/ulid` does not pull in the UUID, TypeID, or KSUID code. Sizes below were remeasured from the same source with `tsdown@0.22.3`, minification, and gzip level 9:

| Import | Minified + gzipped |
| --- | ---: |
| `uniku/uuid/v4` | ~1.2 KB |
| `uniku/uuid/v5` | ~1.8 KB |
| `uniku/uuid/v7` | ~1.7 KB |
| `uniku/ulid` | ~1.9 KB |
| `uniku/typeid` | ~2.9 KB |
| `uniku/cuid2` | ~1.0 KB |
| `uniku/cuid/v2` | ~1.0 KB |
| `uniku/nanoid` | ~1.2 KB |
| `uniku/ksuid` | ~1.5 KB |
| `uniku/objectid` | ~1.6 KB |
| `uniku/tsid` | ~1.7 KB |
| `uniku/xid` | ~2.1 KB |
| `uniku/errors` | ~445 B |
| `uniku/generators` | ~101 B |

The CUID v2 entry point imports SHA3-512 from `@noble/hashes`, uniku's one runtime dependency; the size above excludes that external dependency's own weight. The UUID v5 entry point inlines its SHA-1, so its size includes the whole hash and it has no runtime dependency.

## Reproduce these numbers

Run the benchmark and bundle-size tooling from the repository root:

```sh
pnpm --filter uniku bench:compat
pnpm bench:summary
pnpm bundle:summary
pnpm --filter uniku bench:cold-start
```

`bench:compat` runs uniku and the reference packages in separate processes; `bench:summary` reads those results and prints a comparison table. CI repeats the compatibility run four times with balanced launch orders. `bundle:summary` builds each entry point and reports its minified, gzipped size. `bench:cold-start` measures fresh-process startup separately from warmed generation throughput.
